# Задание 2

## Стратегия миграции данных при запуске нового сервиса

Новый сервис запускаем по шагам ADR-002 (`tasks/task1/results/ADR-002-booking-first.md`). Данные переносит временная задача миграции - скрипт, который запускает DevOps. Бронирования в монолите только добавляются и не меняются, поэтому при повторном запуске задаче достаточно перенести записи с `id` больше последнего перенесённого: следить за изменениями уже перенесённых записей не нужно.

1. **Подготовка.** Поднимаем `booking-service` с пустой `booking-db`: схему создают миграции goose, встроенные в сервис. Монолит в это время работает как раньше.
2. **Начальная копия.** Пока монолит работает, задача миграции копирует все бронирования:
   - задача копирует бронирования с их прежними `id`, а не получает новые из последовательности `booking-db`, потому что клиенты уже знают номера своих бронирований;
   - у части бронирований монолит не заполнил дату создания, и задача ставит вместо неё время миграции: монолит, который после переключения читает бронирования из `booking-service`, не может обработать бронирование без даты и вернёт ошибку;
   - последовательность `id` в `booking-db` начинается с 1 000 000 000 - это отдельный диапазон для бронирований сервиса; если `id` монолита уже дошли до этого диапазона, задача останавливается с ошибкой и ничего не копирует;
   - после копирования задача сверяет количество бронирований из диапазона монолита и сумму их цен.
3. **Дозагрузка новых записей.** При повторном запуске задача переносит бронирования монолита с `id` больше последнего перенесённого, но меньше начала диапазона сервиса, и снова сверяет данные.
4. **Переключение без простоя.** Запускаем непрерывную дозагрузку новых записей раз в несколько секунд и обратную синхронизацию `legacy-booking-sync`. Затем поочерёдно перезапускаем экземпляры монолита с переменными `BOOKING_SERVICE_EXTERNAL_HOST/PORT`: с ними монолит перестаёт работать со своей таблицей бронирований и передаёт запросы в `booking-service`. Пока одни экземпляры уже пишут в `booking-service`, а другие ещё в монолит, идентификаторы не пересекаются, потому что сервис выдаёт `id` из своего диапазона. По той же причине задача не копирует обратно бронирования, которые `legacy-booking-sync` записал в монолит. Когда все экземпляры монолита начали писать в `booking-service`, выполняем последнюю дозагрузку со сверкой и останавливаем задачу миграции.
5. **Проверка.** Прогоняем `regress.sh` в режиме booking-service и следим за ошибками и временем ответа при создании бронирования.
6. **Откат.** Так же поочерёдно перезапускаем экземпляры монолита, но уже без этих переменных, и монолит снова работает со своей таблицей. Бронирования, созданные в `booking-service`, в этой таблице уже есть: их туда записывает `legacy-booking-sync`.

## Стратегия To Be

После запуска `booking-service` развиваем систему так, как описано в ADR-001:

- **Синхронизация в legacy-таблицу на время отката.** Подписчик `legacy-booking-sync` читает топик `booking.events` и записывает бронирования в таблицу `booking` монолита. После периода стабильной работы подписчика удаляют вместе с legacy-таблицей.
- **Список бронирований без `userId`.** Сейчас запрос всех бронирований через монолит завершается ошибкой 500: если в запросе нет `userId`, прокси монолита падает с ошибкой и запрос не доходит до `booking-service`. Нужно исправить прокси или получать список не через монолит, а напрямую из `booking-service`, например через BFF фронтенда.
- **Устойчивость обращений к монолиту.** Сейчас у REST-вызовов есть только таймауты по 2 секунды. Нужно добавить circuit breaker и ограниченное число повторов. После этого сервис будет хранить локальные копии данных пользователей, отелей и промокодов и обновлять их по событиям, чтобы бронирование не зависело от доступности монолита.
- **История и аналитика.** `booking-history-service` остаётся единственным источником статистики. Когда появятся `BookingCancelled` и другие события, сервис будет обрабатывать их так же идемпотентно. Отдел аналитики будет получать данные через REST или выгрузку в DWH, а не прямыми SQL-запросами.
- **Kafka.** Топики создаёт сервис, которому они принадлежат, а автоматическое создание топиков на брокере выключено. В продакшене нужен кластер из трёх и более брокеров с `replication.factor = 3` и `min.insync.replicas = 2`.
- **Платформа.** Kubernetes, Helm и CI/CD, service mesh для canary-релизов и отказоустойчивости, разделение оставшихся БД и переезд в облако.
